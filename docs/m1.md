# Milestone 1 — the review loop on PRs

> History: what the milestone shipped. Since then the reviewed marks (Mark reviewed, per-file
> marks and progress, "Since your review", "changes to review") and the agent review guide were
> removed, and the Inbox sections were redesigned; the README describes the app as it is.

One connected repository; your open pull requests are the work items.

## What it does

- **Connect a repo:** point Ariekei at a local clone. It finds the GitHub remote (`origin`, else
  `upstream`, else any GitHub remote) and uses your `gh` login.
- **Inbox:** your open PRs, polled from GitHub every 60 s (↻ refreshes now), ordered by what needs
  you: agent waiting for permission → CI failing → new reviews/comments since you last opened the
  item → agent finished with unreviewed changes → agent working → the rest by last update.
  Each row shows CI, draft, review decision, unresolved threads and agent status.
  Polling is cheap on GitHub's GraphQL budget (5000 points an hour, shared with `gh` and the
  agents): it asks which PRs exist and when each last changed (1 point per query) and fetches
  details only for PRs that changed, are new, or have checks running; every tenth poll and ↻
  fetch them all. If the budget is used up anyway, the Inbox says so and polling waits for
  GitHub's reset.
- **Start working:** one click per PR. Creates `../<clone>_pr<N>` on the PR's branch, tracking the
  PR head (fetched from the head repository's remote, added like `gh pr checkout` if missing), so a
  plain `git push` updates the PR. Reuses an existing worktree that has the PR's branch, `pr-<N>`,
  or a branch tracking the PR head. A reused local branch is fast-forwarded to the PR head; if it
  has its own commits it is left as it is and the UI says so.
- **Agent:** your installed `claude` in the worktree (see `docs/spike-results.md`, agent
  integration v2). A new conversation gets the PR as context via `--append-system-prompt-file`:
  description, unresolved review threads with file/line, review summaries, failing checks with the
  failing part of the Actions job log. The agent waits for your instructions. Claude Code records
  the system prompt at the conversation's first request, so the context is frozen there; **Send PR
  feedback to agent** sends the current threads, reviews and CI state as a message.
- **Review:** changes since your last review (or the PR's merge base before the first), including
  uncommitted ones, or any single commit since then. Chunks come from git's own hunks
  (CodeMirror's diff only adds character-level detail inside them). Select code on the right to
  attach a comment; **Send N comments to the agent** delivers them as one message. **Mark
  reviewed** moves the marker to HEAD and also writes `refs/ariekei/reviewed/pr-<N>` in the clone,
  so the commit stays reachable after the agent rebases. When viewing the working tree, the right
  side is editable and can be saved.
- **Switching and resume:** each item's tab, review scope, selected file and pending comments are
  stored with the item. Terminals keep running while you look at other items. A terminal nobody
  looks at whose agent has been waiting for 15 minutes is closed, unless the agent still runs
  processes of its own (e.g. background shells, which would end with it and which resuming does
  not restart); opening the item resumes the conversation (`--resume`). Restarting the app does
  the same.
- **Notifications:** an OS notification when an agent waits for permission, finishes a turn or
  stops with an error, when a PR's CI starts failing, and on new reviews or comments. Nothing for
  the item you are looking at in a focused window. While an Ariekei window is focused, the
  notice shows in that window instead (an OS notification is easy to miss with the app in
  front); clicking it opens the item.

## M1.1 additions

- **Other people's PRs** (the sections have since been redesigned, see the README): the Inbox has sections **Mine**, **Review requested** and **Opened**
  (PRs you opened from search; any PR you open stays listed even after the review request is gone).
  The search box searches all open PRs of the repo with GitHub's search syntax (words, `#123`,
  `author:name`, …).
- **Work item tabs:** **Overview** (title, author, branches, labels, description, reviewers,
  checks) · **Comments** (review threads by file with their diff snippet, unresolved first; the
  conversation; reply, resolve/unresolve, new comment) · **Review** · **Terminal** (with a
  worktree). GitHub renders the markdown; Ariekei sanitizes it (DOMPurify) and opens links in the
  system browser.
- **Reviewing without a worktree:** opening a PR fetches GitHub's `refs/pull/<N>/head` into the
  clone as `refs/ariekei/pull/<N>/head`; no checkout, no agent. **Start working** (header) creates
  the worktree and agent for any PR.
- **Review scopes:** **All changes vs `<base>`** (merge base → head, like GitHub's Files tab),
  **Since your review** (when marked) and each commit (new ones since your review highlighted).
- **Review comments → GitHub or agent:** drafts are collected per item; **Submit to GitHub…**
  sends them as a review (Comment, or Approve / Request changes on others' PRs). Drafts on lines
  of the PR diff at its head commit become line comments; the others are listed in the review
  text and the panel says which is which. **Send to the agent** remains for items with a worktree.
- E2E: `e2e/review_scenario.py` runs against `e2e/fake_gh.py` (set `ARIEKEI_GH`), which serves
  fixture PRs and records every write; the scenario checks the exact review payload. Verified on
  besu read-only: search, Overview, Comments and review of another author's PR (#11206).
- Not covered yet: pending (multi-session) GitHub reviews, suggestions, comments on deleted lines
  (left side), editing or deleting your comments, and a markdown preview for what you write.

State lives in SQLite (`ariekei.db` in the app data dir); worktrees, branches and the review refs
live in your clone.

## Testing

- `npm run check`, `npm test` (git-hunk → CodeMirror mapping), `cargo test` in `src-tauri`
  (store, GitHub parsing, worktree create/adopt/fast-forward against a fake GitHub remote, inbox
  ordering, hooks, context rendering, notifications).
- Live, read-only GitHub check: `ARIEKEI_LIVE_REPO=owner/name cargo test -- --ignored live`.
- E2E on a local fixture (`e2e/m1_scenario.py`, run with `e2e/run.py`; the agent is the fake in
  `e2e/fake_claude.py`): connect, Inbox, Start working, slash-command autocomplete, an agent
  commit after a permission prompt, review since base, Mark
  reviewed, a second commit showing up alone, Inbox attention, idle shutdown (not while a background job
  runs) and resume, restart.
  Test-only env: `ARIEKEI_DATA_DIR`, `ARIEKEI_NO_POLL`, `ARIEKEI_IDLE_SECS`, `ARIEKEI_CLAUDE_ARGS`.
- Verified on besu: Inbox with 23 PRs, Start working on #11577 (worktree created on its branch in
  ~5 s, agent ready ~1.5 s later, context written), Review since the PR base.

## Known gaps

- Not exercised end to end: the comment selection UI (its delivery path, `agent_send`, is),
  **Send PR feedback to agent** against real GitHub, and notifications on a real desktop (Xvfb has
  no notification daemon).
- The first time Claude Code sees a repository it asks for trust in the terminal, with "No, exit"
  preselected.
- Out of M1, as planned: issues → branch → draft PR, cleanup of finished items (closed PRs stay
  listed while they have a worktree), accepting/rejecting single hunks, build/test status in the
  review view, more than one repo. (Java code intelligence is no longer planned: Ariekei is
  language-agnostic, see the README's Roadmap.)
- WebKitWebDriver screenshots take 40+ s on this setup (an X capture of the display shows only
  black under automation), and its synthesized clicks miss elements at the window's bottom edge;
  the scenarios click those in the DOM.
